oh-my-opencode 하네스 구조 분석

상위 경로의 opencode/oh-my-opencode를 기준으로, agent orchestration, category delegation, background task runtime, config merge 구조를 누구나 이해할 수 있게 풀어 쓴 보고서입니다.

분석 대상: oh-my-opencode 비교 대상: ai_dashboard-main 작성일: 2026-07-08

1. 한 문장 요약

oh-my-opencode의 하네스는 “OpenCode 플러그인 런타임 위에 얹은 agent 운영체제”에 가깝습니다.

단순히 agent prompt 몇 개를 등록하는 구조가 아니라, 설정을 읽고, agent를 조립하고, 도구를 등록하고, hook으로 세션 생명주기를 감시하며, task delegation을 별도 세션으로 실행하고, 완료 결과를 부모 세션에 다시 연결합니다.

핵심 설계는 엔진, agent role, category, skill, execution session을 분리한 것입니다. 이 분리가 좋은 확장성을 만듭니다.

3. Config 하네스: 설정이 실행환경으로 바뀌는 과정

oh-my-opencode의 설정은 단일 파일 하나가 아닙니다. user, project, Claude Code 호환 리소스, plugin component를 모두 합쳐 OpenCode 런타임 config에 주입합니다.

flowchart LR
  U[User config
~/.config/opencode/oh-my-opencode.jsonc] --> M[loadPluginConfig]
  P[Project config
.opencode/oh-my-opencode.jsonc] --> M
  M --> V[Zod validation
partial fallback]
  V --> C[createConfigHandler]
  C --> P1[applyProviderConfig]
  C --> P2[loadPluginComponents
Claude Code plugins]
  P2 --> A[applyAgentConfig]
  A --> T[applyToolConfig]
  T --> MCP[applyMcpConfig]
  MCP --> CMD[applyCommandConfig]
  CMD --> R[Mutated OpenCode runtime config]

중요한 디테일

  • src/plugin-config.ts는 project config가 user config를 override하게 합니다.
  • 잘못된 config section이 있어도 전체 로딩을 죽이지 않고, 가능한 section만 부분 로딩합니다.
  • applyAgentConfig는 built-in agents, user/project Claude agents, plugin agents, 기존 OpenCode agents를 모두 합칩니다.
  • 기본 agent를 Sisyphus로 바꾸고, 기존 OpenCode build/plan agent는 숨기거나 demote합니다.

좋은 점: 설정 로딩과 실행환경 주입이 분리되어 있어, config UI나 doctor 기능을 만들기 쉽습니다.

주의점: 너무 많은 source를 merge하므로 우선순위와 충돌 설명 UI가 없으면 사용자가 “왜 이 agent가 선택됐는지” 알기 어렵습니다.

4. Agent 모델: 엔진이 아니라 역할이다

oh-my-opencode의 agent는 CLI 엔진이 아니라 “역할(role)”입니다. 예를 들어 sisyphus, hephaestus, oracle, librarian, explore는 각각 다른 작업 성격을 가집니다.

5. Category delegation: 모델 이름 대신 작업 성격을 고른다

하네스의 가장 좋은 설계 중 하나입니다. 호출자는 “GPT-5를 써라”가 아니라 “이 일은 quick이다” 또는 “이 일은 visual-engineering이다”라고 말합니다. 그러면 resolver가 category에 맞는 모델, variant, prompt append, fallback chain을 결정합니다.

flowchart TD
  A[task tool called] --> B{category or subagent_type?}
  B -->|category| C[force agent = sisyphus-junior]
  C --> D[resolveCategoryExecution]
  D --> D1[mergeCategories
defaults + user config]
  D --> D2[resolve model
explicit category model]
  D --> D3[apply fallback requirements]
  D --> D4[category prompt_append]
  B -->|subagent_type| E[resolveSubagentExecution]
  D --> F[buildSystemContent]
  E --> F
  F --> G{run_in_background?}
  G -->|true| H[BackgroundManager.launch]
  G -->|false| I[create sync session + poll]

기본 category 예시

  • quick: 단일 파일, 오타, 작은 변경.
  • deep: 자율 조사와 구현이 필요한 큰 문제.
  • ultrabrain: 복잡한 논리, 아키텍처 판단.
  • visual-engineering: UI, 디자인, CSS, 애니메이션.
  • writing: 문서, prose, 기술 글쓰기.

이 구조는 우리 앱의 Task 모델과 잘 맞습니다. Task.assignee를 CLI 엔진 이름이 아니라 category/profile 기반으로 확장할 수 있습니다.

6. task() 도구의 내부 실행 경로

src/tools/delegate-task/tools.ts가 task delegation의 관문입니다. 이 도구는 인자 검증, skill resolution, parent context resolution, category/subagent resolution, sync/background 실행 분기를 모두 처리합니다.

sequenceDiagram
  participant User as Parent Agent
  participant TaskTool as task() tool
  participant Skill as Skill Resolver
  participant Parent as Parent Context Resolver
  participant Cat as Category/Subagent Resolver
  participant Builder as System Prompt Builder
  participant Exec as Executor
  participant Child as Child Session

  User->>TaskTool: task(category, prompt, load_skills, run_in_background)
  TaskTool->>TaskTool: validate required args
  TaskTool->>Skill: resolve load_skills
  Skill-->>TaskTool: skillContent / notFound error
  TaskTool->>Parent: resolve parent session, model, agent
  Parent-->>TaskTool: parentContext
  TaskTool->>Cat: resolve category or subagent_type
  Cat-->>TaskTool: agentToUse, model, fallbackChain, promptAppend
  TaskTool->>Builder: buildSystemContent
  Builder-->>TaskTool: system prompt content
  alt background
    TaskTool->>Exec: executeBackgroundTask
    Exec->>Child: manager.launch creates async child session
    Exec-->>User: bg task id immediately
  else sync
    TaskTool->>Exec: executeSyncTask
    Exec->>Child: create child session, send prompt, poll idle
    Child-->>Exec: final messages
    Exec-->>User: final text result
  end

중요한 점은 parent context를 보존한다는 것입니다. child session에는 parent session ID, parent message ID, parent model, parent agent, parent tools가 같이 넘어갑니다.

7. BackgroundManager: 하네스의 실행 런타임

src/features/background-agent/manager.ts는 사실상 작은 job runtime입니다. task를 queue에 넣고, 동시성을 제한하고, OpenCode child session을 만들고, prompt를 비동기로 던지고, polling으로 완료를 감지합니다.

stateDiagram-v2
  [*] --> pending: launch()
  pending --> queued: add to queuesByKey
  queued --> running: acquire concurrency + create session
  running --> completed: session idle + result captured
  running --> error: prompt/session/model error
  running --> interrupt: aborted/stale/error interruption
  running --> cancelled: cancel requested
  error --> pending: fallback retry available
  completed --> notified: parent notification queued
  interrupt --> notified
  cancelled --> notified
  notified --> cleanup: delayed cleanup
  cleanup --> [*]

내부 상태

  • tasks: task id에서 BackgroundTask로 가는 registry.
  • queuesByKey: model/provider 또는 agent 기준 queue.
  • ConcurrencyManager: provider/model별 동시 실행 제한.
  • taskHistory: parent session별 task 기록.
  • pendingByParent, notifications: 부모 세션 알림 batching.

8. 관찰 가능성: background_output과 metadata

백그라운드 task는 즉시 결과를 반환하지 않습니다. 대신 task id를 반환하고, 나중에 background_output으로 상태나 전체 세션을 읽습니다.

sequenceDiagram
  participant Parent as Parent Agent
  participant Manager as BackgroundManager
  participant Child as Child Session
  participant Output as background_output

  Parent->>Manager: launch task
  Manager-->>Parent: bg task id
  Manager->>Child: create session + promptAsync
  Child-->>Manager: messages, tool calls, idle events
  Parent->>Output: background_output(task_id)
  Output->>Manager: getTask(task_id)
  Output->>Child: fetch session messages
  Output-->>Parent: full session or summarized result

create-background-output.ts는 task 상태가 active이면 thinking/tool result를 더 포함하고, 완료 후에는 full session 또는 task result를 format합니다. 이 덕분에 parent agent는 context window를 과하게 쓰지 않고 필요할 때만 child 결과를 가져옵니다.

10. 우리 ai_dashboard에 반영할 때의 설계

반영 1: AgentKind는 그대로 둔다

claude | codex | opencode는 CLI 엔진 선택 전용으로 유지합니다. sisyphus, oracle은 절대 AgentKind에 넣지 않습니다.

반영 2: AgentProfile 확장

현재 AgentProfileSchema에 category, skills, variant, fallbackModels를 추가합니다.

반영 3: Category resolver 추가

Task의 성격을 quick/deep/wikigen/review/git 같은 category로 해석하고 실행 profile을 결정합니다.

반영 4: Config merge

project config, user config, default config를 merge한 결과를 UI에서 보여줍니다.

반영 5: Run runtime 분리

DevHarnessService에 queue, status, transcript, cancellation, concurrency를 더 명시적으로 분리합니다.

반영 6: 관찰 가능성

각 child run의 transcript, category, model, skill, parent task를 DB에 남기고 UI에서 추적합니다.

11. 단계별 적용 로드맵

  1. Read-only discovery부터 확장: OpenCodeConfigAdapter가 .opencode/oh-my-opencode.jsonc의 agents, categories, skills를 읽게 합니다.
  2. 공용 schema 추가: AgentCategory, CategoryConfig, SkillRef, ResolvedAgentProfile를 shared schema로 둡니다.
  3. Resolver 추가: project/user/default config를 합쳐 “왜 이 모델과 profile이 선택됐는지” 설명 가능한 resolver를 만듭니다.
  4. UI 추가: Agent Config 화면에 category, model, skills, source priority를 보여줍니다.
  5. DevHarness 연결: workflow?: string 중심에서 category/profile/skills 중심으로 확장합니다.
  6. 실행 런타임 강화: concurrency, cancellation, retry, result fetch를 AgentRunRuntime 같은 별도 모듈로 뺍니다.

12. 결론

oh-my-opencode의 하네스 구조는 우리 앱에 그대로 복사할 대상은 아닙니다. OpenCode plugin API에 깊게 묶인 부분이 많기 때문입니다. 하지만 개념 구조는 매우 좋습니다.

  • 가져올 것: role-based agent, category delegation, skill injection, config merge, background run runtime, result retrieval.
  • 그대로 가져오면 안 되는 것: OpenCode plugin hook API, Sisyphus prompt 내부 정책, 모델별 강한 하드코딩.
  • 우리식으로 바꿀 것: Electron/SQLite/IPC 기반의 project task orchestration으로 재해석합니다.
최우선 구현 후보는 “oh-my-opencode config discovery + category/profile schema 확장 + Agent Config UI”입니다. 이 세 가지를 먼저 하면, 이후 DevHarnessService를 category 기반 하네스로 자연스럽게 확장할 수 있습니다.

13. 추가 확인: lifecycle hook과 direct agent invocation

백그라운드 탐색 결과, 보고서 본문에 적은 구조 외에 두 지점이 특히 중요합니다.

Lifecycle event dispatcher

src/plugin/event.ts가 런타임 이벤트의 중앙 fan-out 지점입니다. session.created, session.deleted, message.updated 같은 이벤트를 받아 session state, tmux, MCP, fallback, tool metadata, task continuation hook으로 나눠 보냅니다.

Direct agent invocation

src/tools/call-omo-agent/tools.ts는 category가 아니라 특정 agent를 직접 호출하는 경로입니다. 반면 src/tools/delegate-task/tools.ts는 category/subagent 선택, skill 주입, fallback chain, sync/background 분기를 처리하는 더 높은 수준의 dispatcher입니다.

flowchart TD
  EV[OpenCode runtime event] --> EH[src/plugin/event.ts]
  EH --> S1[session state cleanup/setup]
  EH --> S2[tmux session mirror]
  EH --> S3[MCP disconnect/cleanup]
  EH --> S4[model fallback hooks]
  EH --> S5[continuation/todo hooks]
  EH --> S6[tool metadata/session tools]

  AG[Agent request] --> KIND{Invocation kind}
  KIND -->|direct agent| CA[call_omo_agent]
  KIND -->|task category/subagent| DT[task delegate tool]
  CA --> BG[background executor]
  CA --> SY[sync executor]
  DT --> RES[category/subagent + skill + model resolver]
  RES --> BG
  RES --> SY

따라서 우리 앱에 반영할 때도 execution runtime과 lifecycle event dispatcher를 분리하는 편이 좋습니다. 실행은 run/session을 만들고, event dispatcher는 상태 변화와 cleanup을 책임지게 하면 구조가 단순해집니다.

분석에 사용한 주요 파일: src/index.ts, src/create-managers.ts, src/create-tools.ts, src/create-hooks.ts, src/plugin-interface.ts, src/plugin-handlers/config-handler.ts, src/plugin-handlers/agent-config-handler.ts, src/tools/delegate-task/tools.ts, src/features/background-agent/manager.ts, src/plugin/tool-registry.ts.
